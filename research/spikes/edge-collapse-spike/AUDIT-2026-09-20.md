# edge-collapse-spike audit — 2026-09-20

Founder report after `./run.sh`: "completely no glass gradient, no SwiftUI
animations, not one continuous smooth motion; rough." This audits the
code-level reasons, file:line, against the earlier `glass-morph-spike`
(which has real positive evidence of glass rendering + morphing on the same
kind of transparent `NSPanel`).

All line numbers below are against this worktree's current
`research/spikes/edge-collapse-spike/Sources/EdgeCollapseSpike/*.swift` and
`research/spikes/glass-morph-spike/main.swift`.

---

## 1. Is `.glassEffect` reached at runtime?

Only in **one** of the spike's five states — `.floating` — and only through
`FloatingBodiesView.swift:41-59`:

```swift
if #available(macOS 26.0, *) {
    GlassEffectContainer(spacing: ...) { ... }
} else {
    // Pre-macOS 26 ... Solid dark fallback
    horizontalBodiesFallback / verticalBodiesFallback
}
```

The README (this spike's own note, written after a real launch) records
`this machine's screen ... macOS 26.2`, so the `#available` gate itself is
almost certainly `true` at runtime and the fallback branch is **not** the
reason glass never appears. `Package.swift:6-8` pins `platforms: [.macOS(.v14)]`
(vs. `glass-morph-spike`, which has no `Package.swift` at all — it's a
single `swiftc`-compiled file with no deployment-target declaration) but a
`platforms:` minimum only affects what the compiler lets you call
unguarded; it does not change what `#available` evaluates to at runtime on
an actual macOS 26.2 machine. So this is a real difference from
`glass-morph-spike`, but not the explanation for "no glass at all."

The real explanation is architectural: **`.glassEffect` is called nowhere
else in the target.**

```
$ grep -rn "glassEffect" Sources/EdgeCollapseSpike/*.swift
FloatingBodiesView.swift:67,68,75,148,149,155,156
```

Every other body-drawing view is plain `Color`/`Capsule`/custom-`Shape`
fills, with no glass call at all:

- `CardView.swift` (the `.card` state, 28-73): `warmGradient` (a
  `LinearGradient`, `18-26`) — no glass anywhere in the file.
- `TuckedStalkView.swift` (the `.tucked` state, 15-44): `Capsule(...).fill(Color.black)`
  at `25-26` — no glass.
- `RootContentView.swift`'s `pillOverlay` (the `.collapsing`/`.expanding`
  states, `63-76`): `CollapseShape(model.shape).fill(Color.black)` at
  `65-66` — no glass.
- `GooCanvas.swift` (the metaball bridge, mounted during collapsing/floating
  transitions): `Canvas` + `.alphaThreshold`/`.blur` filters, `35-51` — no
  glass, by design (comment `9-16`: "Public API only ... no CABackdropLayer").

So of the five `EdgePresentation` states, **four never touch `.glassEffect`
at all** — `.card`, `.collapsing`, `.tucked`, `.expanding` are 100% flat
black fills / a static gradient. Only `.floating` (reached by hovering over
the tucked stalk) has any glass, and even there it's two small bodies
(a ≤180×32 capsule / 32×32 or 28×64 shapes), not the card or the stalk
themselves. If the founder's pass through `./run.sh` didn't linger in
`.floating` — the README's own driving instructions require a two-finger
scroll *then* a mouse hover over an 8×96 sliver to ever see it — "completely
no glass gradient" is exactly what the code guarantees, independent of any
rendering bug.

Compare `glass-morph-spike/main.swift:80-107`: the ENTIRE content view (pill
+ card) is built from `.glassEffect(...)` calls (`84`, `94`) inside one
`GlassEffectContainer` (`89`). There is no flat-black fallback shape in that
spike at all — everything the window shows is glass. That's why it measured
glass; edge-collapse-spike mostly doesn't call the API in the first place.

### Panel/hosting setup — not the culprit

`EdgeCollapsePanel.swift:60-77` (`makeEdgeCollapsePanel`) matches
`glass-morph-spike/main.swift:116-134` (`makePanel`) on every property that
matters for glass compositing:

| Property | glass-morph-spike | edge-collapse-spike |
|---|---|---|
| `backgroundColor` | `.clear` (126) | `.clear` (69) |
| `isOpaque` | `false` (127) | `false` (70) |
| `hasShadow` | `true` (128) | `true` (71) |
| `styleMask` | `.titled, .resizable, .fullSizeContentView, .nonactivatingPanel` (120) | `.borderless, .nonactivatingPanel, .fullSizeContentView` (63) |
| `level` | `.floating` (124) | `.floating` (67) |
| hosting view | `NSHostingView`, explicit `frame` (405-406) | `EdgeGestureHostingView<...>: NSHostingView`, explicit `frame` (`SpikeAppDelegate.swift:25`) |

No `wantsLayer`/`NSVisualEffectView`/`.ignoresSafeArea` divergence either —
neither spike sets `wantsLayer` explicitly (both rely on `NSHostingView`
being layer-backed by default) and neither uses `NSVisualEffectView` or
`.ignoresSafeArea`. The `styleMask` difference (`.titled/.resizable` vs.
`.borderless`) doesn't affect glass compositing — glass only needs a
non-opaque, layer-backed, `.clear`-background window, which both have. **The
window/hosting setup is not why glass is missing.**

## 2. Is the black overlay drawn above the glass, hiding it?

Yes, but the picture is more specific than "opaque overlay on top of glass" —
there IS an overlay, and separately the shapes it sits above are never glass
to begin with.

`RootContentView.swift:19-50` (the whole panel content, `ZStack`, top of
list = bottom of z-order... SwiftUI's `ZStack` draws later children ON TOP):

```swift
if showsCard { CardView(...) }              // 21-23  bottom
if showsPill { pillOverlay }                // 25-27
if model.presentation == .tucked { TuckedStalkView(...) }   // 29-31
if model.presentation == .floating { FloatingBodiesView(...) }  // 33-35  <- the only glass
if model.gooMounted { gooOverlay }          // 37-39
if showsCard {                              // 41-47  TOP, only during card/collapsing/expanding
    Color.black.opacity(model.blackOverlayOpacity)
        .allowsHitTesting(false)
        .frame(width: cardSize.width, height: cardSize.height)
        .clipShape(RoundedRectangle(cornerRadius: cardCornerRadius, ...))
}
```

`model.blackOverlayOpacity` animates 0→1 during `.collapsing`
(`AppModel.swift:213-215`, `easeIn` over `plan.material.duration` = 100ms,
`EdgeCollapseTokens.collapseBlackOverlayDuration = 0.10`) and 1→0 during
`.expanding` (`AppModel.swift:447-453`, `easeOut`, starting at 90ms). This
black rectangle sits on top of `CardView` (gradient, no glass) and, while
`showsPill` is also true (`.collapsing`/`.expanding`), on top of
`pillOverlay` too (flat black shape, no glass). **It never sits above
`FloatingBodiesView`** — `showsCard` is only true for `.card/.collapsing/.expanding`
(`RootContentView.swift:55-57`), and `FloatingBodiesView` only mounts for
`.floating` (`33-35`), so the two are mutually exclusive; the black overlay
is not literally occluding the one view that does call `.glassEffect`.

So: the overlay masks the card's gradient during the fade (as intended —
that's its job, the design's "material dims the page while the shape
morphs"), but since neither the card nor the pill nor the stalk were ever
glass, there's no glass being hidden underneath it in those states.

`TuckedStalkView.swift:25-26` is confirmed flat black with no glass — even
in `.floating` the STALK itself isn't drawn (only `FloatingBodiesView`'s two
glass bodies are, per `RootContentView.swift:29-35`'s mutually-exclusive
`if`s), so there is no "tucked stalk drawn as plain black shape even in
floating" — the stalk view simply doesn't mount during `.floating` at all.

## 3. How are the transitions driven — why they can't read as one motion

Each of the four transitions in `AppModel.swift` is a **chain of
independently-sprung `withAnimation` calls, staggered by
`DispatchQueue.main.asyncAfter`** (wrapped in the local `schedule(after:generation:)`
helper, `166-172`), not a single `withAnimation` moving one animatable
value. Counts, non-reduce-motion path:

**`runCollapsing` (183-273), total 460ms (`collapseTotalDuration`):**
- 7 separate `withAnimation` calls: content fade/shift (`209`, `.easeOut`),
  black overlay (`213`, `.easeIn`), shape height (`219`, `.spring(response: 0.18, dampingFraction: ~0.90)`),
  hero flight (`227`, `.spring(response: 0.32, dampingFraction: ~0.65)`, fired
  from a `schedule` at `224`), shape width (`235`, `.spring(response: 0.22, dampingFraction: ~0.55)`,
  fired from `233`), shape neck (`243`, `.spring(response: 0.14, dampingFraction: ~0.55)`,
  fired from `241`), shape neck-settle (`249`, `.spring(response: 0.14, dampingFraction: 1.0)`,
  fired from `247`).
- 9 `schedule(...)` (i.e. `DispatchQueue.main.asyncAfter`) calls total in
  this one method (`224, 233, 241, 247, 256, 261, 265, 268, 272`).
- The `shape` field driving `CollapseShape.animatableData` (`CollapseShape.swift:64-75`)
  gets its target reassigned 4 separate times (height-only at `220`,
  width+height at `236`, width/height/corner/neck at `244`, again at `250`)
  by 4 different `withAnimation` blocks with 4 different spring
  `response`/`dampingFraction` pairs. Each new `withAnimation` call
  re-interpolates from wherever the shape's *current* (possibly still
  in-flight) value is toward the new target — so the shape doesn't move
  along `CollapseShapeTrajectory`'s smooth `card→stalk→pill` keyframe curve
  (`CollapseShape.swift:135-141`) at all; **that trajectory table exists in
  the code and is unit-tested (`CollapseShapeTrajectoryTests`) but is never
  called from `AppModel`** — `AppModel.init` only reads
  `CollapseShapeTrajectory.collapsing[0].geometry` once as the *initial*
  value (`AppModel.swift:49`). The actual runtime motion is the 4-spring
  relay above, not the tested trajectory sampler.

**`runFloatingOut` (286-346), total ~180ms:** 4 `withAnimation` calls
(`315` easeOut, `320` easeIn via `schedule` at `319`, `331` spring via
`schedule` at `329`, `336` a second spring with `.delay(s(0.02))` layered
on top of the first — two animations targeting `floatingOvershootScale`
almost simultaneously), 5 `schedule` calls.

**`runFloatingRetract` (350-385), total ~160ms:** 2 `withAnimation` calls
(`370` easeInOut, `378` easeIn via `schedule` at `376`), 2 `schedule` calls.

**`runExpanding` (398-472), total 360ms:** 5 `withAnimation` calls (`429`
spring hero, `434` spring bulge, `441` spring stretch via `schedule` at
`439`, `450` easeOut overlay via `schedule` at `447`, `459` easeIn content
via `schedule` at `457`), 6 `schedule` calls.

**One full card→tucked→floating→tucked→card round trip: 18 separate
`withAnimation` blocks and 22 `DispatchQueue.main.asyncAfter` staggering
calls**, each phase boundary a hard re-target with its own curve. This is
textbook "discrete keyframe track sampled with separate springs, glued by
timers" — exactly the pattern the project's own `CLAUDE.md`/`banned-patterns.md`
warn is unreadable as one motion, just applied here to SwiftUI's declarative
`withAnimation` instead of raw `CAAnimation`. A viewer sees: shape snaps to
a new curve every ~50-90ms, each with a different spring `dampingFraction`
(0.90 → 0.65 → 0.55 → 0.55 → 1.0 in `runCollapsing` alone) — the "personality"
of the motion (how bouncy it feels) changes mid-gesture, which reads as
several small animations chained by a timer, not one continuous gesture,
even though every individual `withAnimation` call is itself smooth.

The README's own "已知未验证" item 3 (this spike's author's own admission)
says the same thing in different words: *"The four `CollapseShape` channels
are not driven by four simultaneous independent springs ... `AppModel`
stages sequential `withAnimation(...)` calls, one per channel ... each call's
spring genuinely only drives the channel(s) whose target it changes at that
instant."*

**View-identity pop at every settle boundary**, compounding the above: at
the end of `.collapsing`, `finishCollapsing()` (`275-282`) fires exactly
when the last `schedule` (`272`, at `totalDuration` = 460ms) runs — it
resizes the window (`panel.setPresentationFrame(... tuckedWindowSize)`,
`278`) and calls `send(.settled)` (`281`), which flips `presentation` from
`.collapsing` to `.tucked`. That single state change simultaneously (a) at
`RootContentView.swift:55-56` sets `showsCard`/`showsPill` false, unmounting
`pillOverlay` — a `CollapseShape` black shape that had just sprung to
`width: 28, height: 120, cornerRadius: 14` (`AppModel.swift:250`) — and (b)
at `RootContentView.swift:29-31` mounts `TuckedStalkView`, an entirely
different view: a `Capsule` fixed at `EdgeCollapseTokens.tuckedSize` =
`8×96` (`EdgeCollapseTokens.swift:28`). There is no `matchedGeometryEffect`
or `glassEffectID` connecting these two shapes — SwiftUI tears down one
subtree and mounts a fresh one, at the exact instant the window itself also
snaps from 250×316 down to 40×128 (`tuckedWindowSize`,
`EdgeCollapseTokens.swift:38-43`). A 28×120 shape hard-cutting to an 8×96
capsule, in lockstep with a window-frame jump, is a visible pop at the
`.collapsing → .tucked` boundary — the same thing happens in reverse
(`.tucked/.floating → .expanding → .card`, and `.floating → .tucked` via
`finishFloatingRetract`, `387-394`). This is the second, independent reason
nothing reads as "one continuous motion": even a perfectly smooth
460ms spring chain still ends in a hard non-animated swap to a differently-
shaped, differently-sized view.

## 4. Same `GlassEffectContainer`+`glassEffectID`, or separate swapped views?

**Separate, `if`/`else`-swapped views — confirmed no shared morph identity
across states.** `RootContentView.swift:19-48` mounts `CardView`,
`pillOverlay`, `TuckedStalkView`, and `FloatingBodiesView` behind four
mutually-exclusive `if` conditions (`21`, `25`, `29`, `33`) keyed off
`model.presentation`/`showsCard`/`showsPill`. Each is a structurally
different SwiftUI view type; SwiftUI diffs them by identity/type, not by a
shared `glassEffectID`, so crossing from one to the next is a mount/unmount,
never a morph.

Only `FloatingBodiesView` uses `GlassEffectContainer` at all
(`FloatingBodiesView.swift:43-49`), and only across its own two bodies
(`glassEffectID("info", ...)` at `69`/`149`, `glassEffectID("control", ...)`
at `76`/`156`) — a real, correctly-scoped glass union for the
`.floating`-internal `floatingSeparation` blend, but it's the only place in
the whole spike doing what `glass-morph-spike` demonstrated. There is no
container spanning card↔pill↔stalk↔floating-bodies, and no `glassEffectID`
shared across states — by construction, **none of the four
state-to-state transitions can use the system's liquid-glass morph.** Only
the hero artwork crosses states via `matchedGeometryEffect` (shared
`heroNS` `Namespace`, e.g. `CardView.swift:38`, `RootContentView.swift:70`,
`FloatingBodiesView.swift:104,184`) — the shape/body chrome around it does
not.

## 5. Window frame: how often does it change, does content re-layout jump?

Exactly twice per transition, both non-animated `setFrame` calls via the
single sanctioned entry point `EdgeCollapsePanel.setPresentationFrame`
(`EdgeCollapsePanel.swift:52-54`, `setFrame(rect, display: true, animate: animated)`,
always called with `animated: false` per `AppModel`'s comments, e.g.
`AppModel.swift:191`):

1. **At transition start** — resize to the LARGER of the two frames
   (design intent: keep the bigger frame for the whole transition, animate
   content inside it): `runCollapsing` → `cardSize` (`190-193`, already
   the current size so this is usually a no-op), `runFloatingOut` →
   `floatingWindowSizeH/V` (`291-296`), `runExpanding` → `cardSize`
   (`403-407`).
2. **At transition end** (`finishCollapsing:277-280`,
   `finishFloatingRetract:388-392`) — snap DOWN to the smaller settled size
   (`tuckedWindowSize`), synchronous with the view-identity swap described
   in §3 above.

So frame changes are not the source of mid-animation jitter (there's no
frame thrash — the code correctly avoids resizing while content animates,
per its own `[PROTOCOL]` comment at `EdgeCollapsePanel.swift:10-12`). The
one frame change that DOES land mid-perception is the end-of-transition
snap-down, and it's made worse by landing at the same instant as the
`CollapseShape`→`TuckedStalkView` (or `TuckedStalkView`→nothing /
`FloatingBodiesView`→nothing) identity swap — two visible discontinuities
(frame size + view identity) stacked on one frame, right when a viewer's
eye is tracking the shape settling into the edge.

## Correct approach for macOS 26 public API

A single `GlassEffectContainer` hosting every body (card / stalk / info /
control) as glass shapes with **stable `glassEffectID`s that persist across
states**, so the system does the liquid blend/morph instead of the app
staging N discrete springs:

1. **One `GlassEffectContainer`, one `Namespace`, bodies mount/unmount
   inside it, never swapped for a structurally different view type.**
   `glass-morph-spike/main.swift:88-107` already proves this: `pill`
   (`glassEffectID("a", in: glassNS)`, line `95`) is always mounted; `card`
   (`glassEffectID("b", in: glassNS)`, line `85`) mounts/unmounts on
   `state.expanded` (line `99-101`) — both inside the same
   `GlassEffectContainer(spacing: 20)` (line `89`). The measured result
   (`research/spikes/glass-morph-spike/results/summary.md`, "animated"
   scenario 1): `RENDER: yes-by-equivalence` (shared `CABackdropLayer`
   class with the founder-verified `NSGlassEffectView` control) and
   `MORPH: yes` — "a layer born after the toggle ... shows 19
   continuously-changing frame-steps between birth and settle." Scenario 2
   (spacing blend inside one always-mounted container, lines `90`, `97-101`)
   also measured `MORPH: yes` — 23 changing frame-steps on the
   pre-existing pill layer alone, i.e. the container-proximity blend (no
   identity change at all) genuinely animates continuously. For
   edge-collapse, the card/pill/stalk/info/control chrome shapes need this
   same treatment: one container, one `glassEffectID` per logical body,
   reused (not recreated) across `.card/.collapsing/.tucked/.floating/.expanding`.

2. **Every state change is ONE `withAnimation(.spring(...))`, not a
   staggered relay.** `glass-morph-spike/main.swift:427-430` drives its
   entire toggle — spacing AND mount/unmount — through exactly one
   `withAnimation(.smooth(duration: 0.4)) { ... }` block. Contrast
   `AppModel.swift`'s 7/4/2/5-call relays per transition (§3 above): collapse
   the edge-collapse choreography to as few `withAnimation` calls as the
   design's distinct target-state changes require — ideally one per
   transition, letting the glass container's own union/split geometry do
   the shape morph the current code hand-animates via `CollapseShape`'s
   4-channel `animatableData`.

3. **Hero via `matchedGeometryEffect` in the SAME namespace as the glass
   bodies** (or at minimum consistently scoped) — edge-collapse-spike
   already does this correctly for the artwork (`CardView.swift:38`,
   `FloatingBodiesView.swift:104,184`, shared `heroNS`); the fix is to give
   the surrounding shape chrome the equivalent continuity via
   `glassEffectID` rather than leaving it as bare `if`-swapped views.

4. **Black→clear tint via `.overlay`/`.tint`, not a full-opacity black
   `Color` layered above non-glass content.** Once the shapes underneath
   are real glass, `RootContentView.swift:41-47`'s `Color.black.opacity(...)`
   approach is directionally fine (it's already `allowsHitTesting(false)`,
   already scoped to the card's own `clipShape`) but should key off the
   same `edgeTint(in:)` pattern `FloatingBodiesView.swift:207-223` already
   uses (gradient vs. flat black, `switch model.tint`) so the material
   read is consistent whether a body is glass or a plain shape mid-morph.

5. **Fixed, oversized, transparent window through a transition — no frame
   changes mid-animation.** The current code already gets this right in
   spirit (§5 above: frame changes only at the two settle boundaries, never
   mid-spring) via `EdgeCollapsePanel.setPresentationFrame`
   (`EdgeCollapsePanel.swift:52-54`) and matches `glass-morph-spike`'s own
   panel, which never resizes at all during its toggle. Keep that contract;
   just also stop the settle-boundary snap from **coinciding** with a
   view-identity swap (§3's second root cause) — e.g. keep the settled
   view mounted (or cross-fade it in via the same glass container) for one
   more frame after the frame-size snap, or size the window to the
   post-settle content BEFORE removing the pre-settle glass body, so the
   window snap and the shape's final glass state land together instead of
   frame-snap-then-pop.

6. **Reduce Motion via `Transaction`, not a parallel bespoke branch per
   transition.** `AppModel.swift` already isolates Reduce Motion into one
   `if reduceMotion { ... return }` per method (e.g. `195-203`); that's
   reasonable, but as the choreography collapses toward one
   `withAnimation` per transition (item 2), Reduce Motion becomes simpler
   to express as `withTransaction` (disabling animation / substituting a
   linear crossfade) wrapping that single call, rather than a fully
   separate literal duplicate of every target-value assignment.

**Bottom line:** `glass-morph-spike` is the existence proof that
`GlassEffectContainer` + `glassEffectID` + one `withAnimation` genuinely
renders and morphs on this exact panel/hosting setup (measured, not
assumed — see `results/summary.md`). `edge-collapse-spike` doesn't fail
because that mechanism doesn't work here; it fails because it never uses
that mechanism for the card/pill/stalk chrome (only for the two floating
bodies), and instead hand-choreographs each transition as a relay of
independently-sprung `withAnimation` calls ending in a non-animated
view-identity swap.
